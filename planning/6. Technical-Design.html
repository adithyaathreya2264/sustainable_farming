System Architecture

Architectural Goal

Deliver a highly scalable, fully custom, offline-first mobile application backed by a dedicated Python environment designed to execute complex machine learning algorithms, manage heavy relational data, and support long-term product growth.

High-Level Architecture Pattern: Local-First Client-Server Architecture

Client (Mobile): The application reads/writes exclusively to a local embedded database. The UI is completely decoupled from network latency.
Synchronization Engine: A background process that negotiates state between the local mobile database and the remote backend when connectivity is available.
Server/Backend: A custom-built, asynchronous Python API layer managing data ingestion, ML processing, and secure communication with the central relational database.

Technology Stack Selection

Central Database MySQL Strict relational database perfect for enforcing data integrity, executing complex joins for financial ledgers, and acting as the ultimate source of truth.

Module Breakdown & Component Architecture

Client-Side Modules (React Native)
  1. Auth Module: Manages the OTP flow and securely stores JWT (JSON Web Tokens) using Expo SecureStore.
  2. Local DB Module: Defines the WatermelonDB schemas and observable queries (e.g., reactive profit calculations). Includes a Map Tile Cache Manager: a utility running alongside Mapbox that automatically triggers a background download of a 5km map radius around the user's saved GPS coordinates whenever the device connects to unmetered Wi-Fi.
  3. Sync Module: Hooks into the WatermelonDB synchronize() protocol. Pushes local changes to the FastAPI backend; pulls remote changes.
  4. Localization (i18n) Module: JSON-based dictionary mapping (EN, KN, HI) managed via the Context API.
Server-Side Modules (FastAPI)
  1. Auth Service: Generates OTPs via MSG91, validates them, and issues JWT session tokens.
  2. Sync Engine API: The core endpoint POST /api/v1/sync. Receives JSON payloads from WatermelonDB, handles conflict resolution, and commits to MySQL via SQLAlchemy.
  3. Proxy Service: Secures third-party calls (Google Maps API, Regional Soil API). The mobile app hits this service to prevent exposing API keys in the mobile binary.
  4. ML & Rules Engine (Worker): Asynchronous background tasks (managed via Celery or APScheduler) that evaluate active FieldPlantings against telemetry data to generate Recommendations.

Domain & Data Design

The system relies on a strict separation of physical schema and logical presentation. All financial and geospatial data is strictly stored in metric/base units in both the local and central databases.

Business Logic Design

5.1 Dynamic Profit Margin Calculation
Rule: Financials are calculated reactively on the mobile client to ensure the dashboard works offline.
Execution:
  1. WatermelonDB observes the interventions table for a specific planting_id.
  2. Sums all records where type == 'Harvest' → Total Income.
  3. Sums all records where type != 'Harvest' → Total Expense.
  4. Computes Net Profit = Income − Expense.
  5. Computes Margin = (Net Profit / Income) × 100 (Handled gracefully if Income is 0 to avoid Division by Zero).
5.2 WatermelonDB to MySQL Synchronization Logic
  1. Client detects network and requests push. Sends local changes to FastAPI.
  2. FastAPI initiates a MySQL Transaction via SQLAlchemy.
  3. FastAPI iterates over client created arrays (INSERT), updated arrays (UPDATE with Timestamp Conflict Resolution: Last Write Wins), and deleted arrays (UPDATE deleted_at = NOW).
  4. FastAPI commits the transaction.
  5. FastAPI queries all rows in MySQL where updated_at > last_pulled_at and sends to client.
  6. Client updates local SQLite DB and marks local records as isSynced = true.

Security Design

Authentication: Passwordless. FastAPI issues standard JWTs signed with a strong backend secret.
Authorization: Every API route (except OTP generation) is protected by a FastAPI Dependency (Depends(get_current_user)). The backend extracts the user_id from the JWT and explicitly checks it against every MySQL query to ensure users can only read/write their own fields and interventions.
Secret Management: MSG91 keys, JWT secrets, and Mapbox's Secret Access Token are stored strictly in a .env file on the deployment server and are never exposed to the client or version control. Mapbox requires two distinct tokens:
  • Public Access Token: Embedded safely into the React Native binary to load the maps.
  • Secret Access Token: Stored strictly in the FastAPI .env file, used if the backend ever needs to securely query Mapbox APIs for geocoding data without routing through the client.
7

Performance & Scalability

FastAPI Async Capabilities: I/O bound operations (like calling the OpenWeather API or MSG91) are handled asynchronously (async def), ensuring the server can handle thousands of concurrent requests without blocking the main thread.
Connection Pooling: SQLAlchemy is configured with a robust connection pool to manage MySQL connections efficiently.
Background Tasks: Heavy machine learning models (e.g., disease prediction algorithms) are offloaded to Celery workers. They do not block the main FastAPI web threads.
8

Reliability & Error Handling

Offline Tolerance: The application assumes the network is hostile. Proxied API calls (like fetching soil) use aggressive timeouts. If it fails, the app swallows the error, saves the raw GPS coordinate locally, flags the row for "Background Retry," and returns a success state to the user.
Transaction Boundaries: The sync push operation in FastAPI is wrapped in a strict SQL transaction. If one client record fails validation, the entire sync batch rolls back to prevent a fragmented database state.
9

Observability

Client Crash Tracking: Integrate Sentry (React Native SDK) to catch and cache offline JavaScript exceptions, uploading them when connectivity restores.
Backend Logging: Use Python's Loguru or standard logging to capture API response times, sync conflict warnings, and ML inference errors.
Monitoring: Expose a /health endpoint in FastAPI to allow infrastructure (like Docker/Kubernetes) to verify the API and MySQL database are successfully connected.

Deployment Design

Client Build: Expo Application Services (EAS) to compile the React Native codebase and push directly to TestFlight and Google Play Console.
Backend Deployment: Containerized via Docker.
Container 1FastAPI Uvicorn Server.
Container 2MySQL Database (with persistent volume).
Container 3Redis (Message broker for Celery).
Container 4Celery Worker (executing the ML models and background tasks).
Reverse Proxy: Nginx handling SSL termination and routing traffic to the FastAPI container.

Testing Strategy

Backend (Pytest): High coverage required for the Sync Engine endpoint (testing conflict resolution, transaction rollbacks, and JWT authorization) and the ML algorithm logic.
Client (Jest & React Native Testing Library): Unit test the Unit Conversion Utility to ensure local unit math is flawless before it hits WatermelonDB.
End-to-End Testing: Manual or scripted testing involving airplane mode toggling to verify the WatermelonDB push/pull payload structure.

Architecture Decision Log (ADL)

IDSubjectDecisionAlternatives ConsideredRationale
ADL-01 Backend Framework FastAPI (Python) Django Chosen over Django. FastAPI provides superior performance for APIs and asynchronous operations, which is critical for handling heavy ML workloads and serving a headless React Native client.
ADL-02 Central Database MySQL — The application requires complex relational mapping (Fields → Plantings → Interventions) to calculate exact financial ledgers. MySQL provides the necessary strict schemas and ACID compliance.
ADL-03 Offline Data Engine WatermelonDB Raw SQLite Chosen over raw SQLite. WatermelonDB provides a proven, reactive sync protocol out-of-the-box specifically optimized for React Native, saving weeks of custom conflict-resolution engineering.
ADL-04 State Management React Context API Redux, Zustand Chosen over Redux or Zustand. The global state requirements (Auth token, UI Language) are simple enough that Context API avoids unnecessary external dependencies and boilerplate.
ADL-05 Mapping API Mapbox React Native Maps, OSM Selected over React Native Maps because of superior offline caching. The ability for farmers to visually see their field boundaries on satellite imagery while offline provides significantly higher user confidence than falling back to a blank GPS grid.
Verification note (ADL-03): WatermelonDB's sync protocol is real and well-documented — it provides the client-side machinery (change tracking, conflict resolution helpers, the synchronize() function). Worth knowing before implementation: it is not fully "out-of-the-box" in the sense of requiring zero backend work — you still need to implement the pullChanges/pushChanges contract on your own FastAPI server (which this document's own Sync Engine API module correctly does). The "saves weeks of engineering" framing holds relative to building a sync engine from scratch, just not in the sense of no backend work being required at all.
Verification note (ADL-05): Mapbox's offline tile caching is real — the @rnmapbox/maps library ships a documented offlineManager API (region packs, ambient cache, tile count limits) that supports exactly the "download a radius around a farm" pattern described here. The 50,000 free map loads/month figure is confirmed current for 2026. One nuance worth flagging before budgeting: that 50,000 figure is Mapbox's web (GL JS) free tier. Mobile SDKs like @rnmapbox/maps are billed by Monthly Active Users rather than by map load, so the actual free-tier math for this app will differ from "50,000 loads" — worth confirming the current mobile MAU allowance directly with Mapbox's pricing page before finalizing budget assumptions.
