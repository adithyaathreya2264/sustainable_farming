Project Plan

Sustainable Farming App

Phase: Project Planning (Finalized) Timeline: 4–6 Weeks
1

Project Objectives & Scope

Execute the MVP defined in the Product Plan: an offline-first mobile app for farmers featuring authentication, field mapping, crop tracking, a rule-based agronomic alert engine, government scheme matching, and automated background data synchronization.

2

Resource Requirements & Roles

Resource 1
Lead Engineer (Solo Coder)
Responsible for all architecture, backend coding, mobile app development, and database implementation.
Resource 2
Product Designer
Responsible for all UI/UX design, wireframing, high-fidelity mockups, and asset exports. (No coding).
Resource 3
Technical Assistant / QA
Responsible for API research (testing MSG91/Govt APIs via Postman), writing the agronomic rules matrix, inputting government scheme data, QA testing, and unblocking the Lead Engineer.
3

Project Methodology: Kanban

We will use a Kanban board (e.g., Trello, Jira) with a continuous flow model.

Backlog→ Design→ To Do (Dev)→ In Progress→ QA (Assistant)→ Done
No Sprints. Tasks move fluidly across the board above.
Work-In-Progress (WIP) Limits: The Lead Engineer should never have more than 2 active coding tasks at once to prevent burnout and context-switching.
4

Work Breakdown Structure (WBS) & Execution Sequence

The WBS is organized sequentially to optimize the critical path.

Phase 1: Foundation & Design Week 1

Designer

1.1Design Auth & Onboarding UI.
1.2Design Field Mapping & Dashboard UI.

Engineer

1.3Setup Cloud Environment (e.g., Firebase or Supabase to drastically speed up backend dev).
1.4Initialize cross-platform mobile repository (React Native/Flutter).
1.5Implement local offline database schema (e.g., WatermelonDB or SQLite).

Assistant

1.6Register and provision API keys (MSG91, Google Maps, OpenWeather).
1.7Create a spreadsheet mapping standard metric units to local units.
Phase 2: Core Engineering & Sync Week 2

Designer

2.1Design Intervention/Ledger Input Forms.
2.2Design Alert/Scheme Notification UI.

Engineer

2.3Implement Phone + OTP Auth flow.
2.4Build the Background Data Sync engine (Crucial early task).
2.5Implement UI for Onboarding & Auth.

Assistant

2.6Test APIs via Postman and document JSON responses for the Engineer.
2.7Build the "Rule-Based Engine" logic matrix (If Temp > X and Humidity > Y = Alert Z).
Phase 3: Application Logic Week 3

Engineer

3.1Implement Field Mapping (Pin drop → API call for baseline soil).
3.2Implement Crop Cycle tracking & local data logging (Interventions/Harvest).
3.3Code the dynamic unit converter.

Assistant

3.4Begin populating the GovernmentSchemes and AgriInputCatalog database tables.
3.5QA test the Auth and Offline Sync on physical devices in Airplane mode.
Phase 4: Prescriptive Engine & Subsidies Week 4

Engineer

4.1Implement Rule-Based Engine logic (running locally or via cloud function).
4.2Implement Government Scheme matching algorithm.
4.3Implement Push Notifications & SMS Fallback via MSG91.

Assistant

4.4End-to-end testing of the Rule Engine (forcing specific weather data to trigger alerts).
Phase 5: Polish & Launch Week 5–6

All Team Members

5.1UI Polish and bug fixing (Engineer/Designer).
5.2Multi-language localization string mapping (Assistant/Engineer).
5.3Final Field Testing – taking the app to a zero-network area (Assistant).
5.4App Store / Play Store deployment (Engineer).
5

Task Dependencies (Critical Path)

1 UI Mockups (Task 1.1) MUST precede Frontend Coding (Task 2.5). The Designer must stay exactly one week ahead of the Engineer.
2 The Rule-Based Logic Matrix (Task 2.7) MUST be completed by the Assistant before the Engineer can code the engine (Task 4.1).
3 The Offline Database (Task 1.5) MUST be stable before Background Sync (Task 2.4) can be built.
6

Risk Register & Mitigation Strategies

Risk Description Likelihood Impact Mitigation Strategy Contingency Plan
Solo Engineer Bottleneck: The single coder becomes overwhelmed, delaying the timeline. High Critical The Assistant must shield the Engineer from all non-coding tasks (API research, DB population, testing). Reduce MVP scope by cutting Government Schemes to V1 if behind schedule by Week 3.
Offline Sync Complexity: Writing a custom sync engine takes weeks to resolve data conflicts. High High Use established BaaS tools (Firebase offline capabilities or PowerSync/Supabase) rather than custom-building syncing logic. Fallback to manual "Tap to Sync" button instead of automatic background sync.
Third-Party API Failures: Govt pricing APIs are down or undocumented. Medium Low The Assistant validates all APIs in Week 1. Use static fallback pricing data for the MVP.
7

Project Assumptions & Constraints

Assumption

The Engineer will utilize Backend-as-a-Service (BaaS) infrastructure rather than writing a custom backend from scratch, enabling the 6-week timeline.

Constraints

Zero budget for external QA or development contractors.
The app must be fully functional offline, requiring mobile development frameworks with robust local storage ecosystems.
8

Quality Management & Definition of Done

Quality Standard: No code is merged to the main branch until it passes a basic offline functionality test.

Definition of Done (DoD) for a Task:

  • ✓UI matches the Designer's specifications.
  • ✓The feature functions seamlessly without an internet connection.
  • ✓The feature successfully syncs data to the cloud when connection is restored.
  • ✓The Assistant has tested the feature on a physical mobile device (not just a web emulator).
9

Change Management Process

Given the tight 4-to-6 week timeline, scope changes are heavily restricted.

1 If a new feature is proposed, the Assistant will evaluate its impact.
2 If it requires more than 4 hours of the Engineer's time, it is automatically pushed to the post-launch "Version 1" backlog.
The MVP scope is locked.
